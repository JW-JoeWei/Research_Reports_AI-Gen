S1 新平台 bring-up 首測

面向內容
情境第一個 BIOS/FW 版本上電,還不知道這條鏈路「還剩多少餘裕」。
建議工具Intel LMT 手動模式[5] + pcilmr -c[4]
怎麼做先 Run_Scan 掃出 BDF、segment 與是否有 retimer;再 pcilmr -c 讀能力,確認 Number of Steps / Max Offset / Independent L-R / Ind Error Sampler / Sample Reporting Method。接著用 Intel 手動模式、dwell 1 秒、ErrCnt 4、步數留空(掃到失敗為止)、RecNum 先量 1(DSP)與 6(EP)兩側。[5][4]
怎麼判讀把「錯誤首次出現的步數」換算成 %UI 與 mV,得到這條鏈路的可用餘裕基準線;這個基準線就是後續 L3 guardband 的起點。
注意步數留空時每次停止點不同,所以首測只做基準、不做判定;要比較時務必固定步數。[5]

S2 卡槽 / 線材 / 連接器矩陣

面向內容
情境要回答:第 3 槽是不是特別差?這條 cable 是否換掉就好?Riser 有沒有問題?
建議工具OCP pci_lmt(config 群組)[2] 或 Google pcie_lmt(eye-scan)[1]
怎麼做把每個變數當成一個群組:lmt_groups[] 內用 name 標記(例如 slot1-riserA、slot1-riserB),bdf_list 列出該變數下的所有埠,bdf 不同就分開量。[2] 若要留眼圖證據,改用 Google 的 eye-scan(start/step/target)輸出 result.html。[1]
怎麼判讀比較同一 lane 編號在不同變數下的錯誤步數;若只有特定變數差,就是該變數的問題;若所有變數都差,懷疑共同項(CPU 側、BIOS 設定)。
注意lane 編號會因反轉而不同,矩陣比較前先確認編號對應方式。[5]

S3 產線抽驗與全檢

面向內容
情境每一台出貨機器都要有 margin 合格紀錄,且必須能在十幾分鐘內完成。
建議工具OCP pci_lmt[2] 或 Google pcie_lmt 的 target_offset 模式[1]
怎麼做固定 error limit(廠商 mask 換算)、固定 samples(如 100 → 10¹⁰ 位元)、固定步數或 target_offset;-o ocptv 讓輸出直接進測試管理系統。[2][1]
怎麼判讀以 L2(廠商 mask)為對外判定、L3(內部 guardband)為良率趨勢管理(見第 10 章)。任一 lane 未達標即攔下,並保留該台的逐 lane 原始資料。
注意不具獨立錯誤取樣器的裝置,OCP 預設不 margining(需 --force),因為可能擾動資料流。[5][2]

S4 維修驗證與 RMA 閉環

面向內容
情境換了 cable/retimer/卡之後,要證明根因真的修好了,而不是換了零件運氣好。
建議工具與 S3 完全相同的工具與 spec(重跑)[2]
怎麼做維修前先量並存檔(建立 baseline);維修後用同一份 config/spec 重跑;兩份結果逐 lane 對照。[2][3]
怎麼判讀修復的標準是「該 lane 的錯誤發生步數回到同型號正常分布內」,而非單純「這次通過」。OCP 的框架目標之一就是讓同一份診斷可在整個生命週期重複使用,並可結合修復自動化。[3]
注意維修後若 BIOS/FW 也變了,必須在紀錄中標明,否則前後不可比。[5]

S5 溫度角落驗證

面向內容
情境實驗室常溫會過,但機房滿載後是否還夠?
建議工具同 S2/S3 的設定,差別只在量測時機[1]
怎麼做在冷機(開機後立即)與熱機(穩定負載後)各量一輪,其餘參數完全不變;工具與參數固定後,差異就只剩溫度因素。
怎麼判讀比較兩輪的錯誤發生步數差距;若熱機餘裕消耗過大,代表 guardband 要加寬或散熱/風流要調整。
注意★ 這是最容易被忽略但最常見的現場失效來源;本報告建議列為新平台必要驗證項目。

S6 多卡 GPU / 多 NIC 全鏈路

面向內容
情境一台機器有數十條 ≥16 GT/s 鏈路,要找出「哪條特別差」而不是逐條慢慢量。
建議工具pcilmr --full[4] 先快篩,再用 OCP 群組逐一確認[2]
怎麼做pcilmr --full 對系統中所有 Ready 的鏈路逐一 margining[4];再用 lspci -tv/pci_crawler 畫拓樸,把 root port / switch / GPU / NIC 分組[2]
怎麼判讀先看哪些鏈路 fail,再對這些鏈路用 OCP 做分組精確量測並產出報表。
注意並行量測(Google 的 lane/link-parallel、pcilmr 的 -p)可加速,但需先做一致性驗證。[1][4]

S7 客訴 / 機房異常複現

面向內容
情境客戶說某台機器降速或有錯誤,但回廠後量不到問題。
建議工具Intel LMT(可觀察每一步,最適合複現)[5] + pcilmr(現場環境)[4]
怎麼做先確認鏈路當下的速率與寬度(是否已降速降寬);再以手動模式逐 lane 觀察,並檢查結果中的 lane reversal 與 NA 欄位是否揭示接線/能力差異。[5]
怎麼判讀若無法複現,重點是保留證據:同一組 BDF/lane 加上 BIOS/FW 版本,並比對客戶端與廠內的量測條件差異(溫度、負載、機櫃位置)。
注意★ 建議把量測條件(BIOS/FW/溫度/負載/工具版本)一起寫進報告,否則事後無法比對。

S8 供應商來料評比

面向內容
情境同一規格的兩家 cable/retimer/SSD,要用同一把尺比較。
建議工具Google pcie_lmt 或 OCP pci_lmt,固定同一份 spec/config[1][2]
怎麼做同一份 spec 內只換 BDF(不同受測樣品),其餘參數完全不動;samples 與 error limit 取兼顧時間與解析度的組(見第 09 章 profile B)。[1][2]
怎麼判讀比較錯誤發生步數的分布(中位數與最差 lane),而不是平均;用分布下緣當選商依據。
注意★ 建議同時保存 pcilmr 的內建分級結果當第二意見,避免單一工具的系統性偏差。[4]
★ 結論 · 八個場景的共同結構

每個場景其實都是同一個迴圈:固定條件 → 讀能力 → 量測 → 跟基準比 → 保留原始資料。工具可以換,這個結構不能省。特別是「保留原始資料」——OCP 框架之所以值得採用,正是因為它讓這一步變成規格化的輸出,而不是工程師手動整理。[3]
