擴充能力與暫存器位置

LMR 以 PCIe 擴充能力結構呈現,Extended Capability ID = 0x27。Linux kernel 的實作(2026 年 patch)直接列出各欄位在能力結構內的位移:[10]

位移(相對能力起點)名稱欄位來源
0x04Margining Port Capabilitiesbit0 = Uses Software Ready[10]
0x06Margining Port Statusbit0 = Margining Ready;bit1 = SW Ready[10]
0x08Margining Lane Control(每 lane 一字)見下表[10][1][2]
0x0AMargining Lane Status(每 lane 一字)見下表[10][1][2]
stride = 4lane 之間的暫存器間隔每條 lane 一組 Control/Status[10]

Margining Lane Control 欄位

欄位bit意義來源
Receiver Number[2:0]0 = 本地接收器;1–6 = DSP/USP/retimer 各接收器;7 = 保留(0..6,共 3 位元)[10][5]
Margin Type[5:3]命令類型(見下節)[1][10]
Usage Model[6]使用模型;規格要求一般操作為 0,暫存器存取類命令另用[1][2]
Margin Payload[15:8]方向位 + 步數,或報告/設定命令的參數[1][2]

payload 的方向位與步數

  • 時間:payload[6] = 方向(0 = 往右、1 = 往左),payload[5:0] = 步數;若裝置不支援獨立左右,方向位保留,步數代表「距正常位置幾步」[2]
  • 電壓:payload[7] = 方向(0 = 上、1 = 下),payload[6:0] = 步數;若裝置不支援獨立上下,方向位保留[2]
  • Google 實作以遮罩表示同一件事:方向遮罩電壓 = 0x80、時間 = 0x40[1]
注意 · 獨立左右/上下會改變欄位語意

讀取資料時務必先看能力位元(Independent Left/Right Timing、Independent Up/Down Voltage)。若為 0,回報的方向欄位「可能」是 NA,而步數的意義也不同——Intel 指南特別說明結果檔案中 NA 欄位正是由這個能力位元決定。

[5][2]

命令類型(MTYPE)

Google 原始碼明確標註此編碼依 PCIe 5.0 Spec §4.2.13.1:[1]

MTYPEGoogle / OCP 命名payload 用法實務用途
0x7No Command固定 0x9C命令之間必須先廣播;確認鏈路回到正常取樣[1][2]
0x1Report暫存器位移 0x88–0x90讀取能力與步數、取樣率、取樣計數、最大 lane 數[1][2]
0x2Set0xC0|限制值、0x0F、0x55設定錯誤上限、回歸正常設定、清除錯誤日誌[1][2]
0x3Timing方向位[6] + 步數時間方向的 step margin[1][2]
0x4Voltage方向位[7] + 步數電壓方向的 step margin[1][2]
0x0(未使用)—Google 實作未使用此值[1]
0x5(未使用)—Google 實作未使用此值[1]
待查 · ★ 兩個開源實作對 MTYPE 的理解不同(必查)

Linux kernel patch 的列舉值為:DEMARGIN 0x0、REPORT_CAPS 0x1、REPORT_VOLTAGE_STEPS 0x2、REPORT_TIMING_STEPS 0x3、TIMING 0x4、VOLTAGE 0x5、NO_CMD 0x7。[10] 而 Google(標註依 5.0 §4.2.13.1)與 OCP 實作則為 Report = 1、Set = 2、Timing = 3、Voltage = 4。[1][2]
兩者在 0x2–0x5 的語意不同,可能源自規格版本差異(r5.0 §4.2.13.1 vs r6.0 §8.4.4),本報告未取得規格原文逐條核對,因此標為待查。若你要自己實作 LMR,請務必以手上的規格表確認此欄位。

進階 · OCP 另外支援「跨 retimer 的暫存器存取」

OCP 實作中有 access_retimer_register():以 MTYPE = 0x1、payload = 暫存器位移,可讀取 retimer 內部位移 0x0–0x87 / 0xA0–0xFF 的暫存器值。這在需要讀 retimer 內部狀態時很有用,但需注意 payload 位移的合法範圍。

[2]

設定用命令 payload

命令payload作用來源
Set Error Count Limit0xC0 | (限制值 & 0x3F)設定錯誤上限;同時也是計數重設的觸發點[1][2]
Go To Normal Settings0x0F接收器回歸預設取樣位置(margining 後收尾必做)[1][2]
Clear Error Log0x55清除錯誤日誌,讓下一次量測從乾淨狀態開始[1][2]
No Command0x9C(搭配 MTYPE = 0x7)命令之間的強制廣播[1][2]

回應狀態與錯誤計數

回應放在 Control 位址 + 2 的狀態字;其中 payload[7:6] 為執行狀態、payload[5:0] 為錯誤計數。[1][2]

payload[7:6]狀態意義工具的處理
00錯誤溢位(Error Out)錯誤過多,接收器自行回到預設設定;錯誤計數可能大於設定上限視為該偏移不合格,記錄錯誤數[1][2]
01設定中(Setting Up)接收器正在準備,尚未開始 margining;錯誤計數為 0繼續輪詢[1][2]
10Margining 進行中正在執行該步命令,錯誤計數開始累計等待下一狀態或逾時[1][2]
11NAK命令不被支援(例如要求超出 ±0.2 UI 的時間偏移);錯誤計數為 0視為「此偏移無效」並停止該方向,常代表步數超出能力[1][2]

錯誤計數為 6 位元、飽和於 63;並且在收到新的 margin 命令時歸零。若裝置支援獨立錯誤取樣器(Ind Error Sampler = 1),計數的是真正的位元錯誤;否則算的是邏輯錯誤,而且 margining 本身可能在正常資料流上產生錯誤——這是產線環境必須先確認的事。[5][2]

時序與逾時限制

參數來源值說明
命令間隔(最小值)≥10 µs(Google 實作取 12 µs)連續命令之間必須留白,否則接收器可能漏收[1]
命令逾時(最小值)≥10 ms(Google 實作取 12 ms)等待回應的上限[1]
kernel 命令逾時150 ms;輪詢間隔 100–250 µskernel 實作的等待策略較寬鬆[10]
kernel 啟用逾時150 ms;輪詢間隔 1000–2000 µs等待 Margining Ready 的時間[10]
OCP 命令逾時0.5 秒(常數 TIMEOUT)OCP 實作以 Python 時間判斷[2]
Intel dwell 建議每個 offset 之間等 1 秒(依規格)Intel 指南描述「wait one second between margining steps」[5]
實作重點 · No Command 廣播不是可選項

Google 實作把「先廣播 No Command 並確認回應」放在每個命令之前(lmrCmdRsp 流程),kernel 也以 MTYPE = NO_CMD 的寫入與等待作為命令前置條件。[1][10]這一步若省略,常出現「命令下得去但狀態讀不到」的現象。

工具存取路徑備註來源

★ 建議 · ★ 這對「要不要自己做工具」的意義

LMR 的控制/狀態面是標準化的 16-bit 暫存器存取,因此自製工具在技術上可行(OCP 版本甚至是純 Python + setpci)。真正的成本在於:能力解析、方向語意、逾時重試、以及結果的統計與報表——這正是四個開源/廠商工具已經幫你做完的部分。[1][2][10]
